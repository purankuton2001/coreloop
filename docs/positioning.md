# コンセプトと競合 — 何のためのパッケージか

## 1. 売っているもの

**人の思想を言語化し、その人自身のブランドに変え、シェアされることで次の人を連れてくる。**
そのループを他人のプロダクトに埋め込めるようにするエンジン。

```
Dig（掘る）        面談・1問1画面・音声。素材を集める
  ↓
Verbalize（言語化） 候補を3つ出す → 却下 → 掘り直す → 確定。本人が選ぶ
  ↓
Brand（ブランド化） 二つ名・物語・強み・軸。公開IDと公開粒度
  ↓
Share（シェア）     確定した瞬間・伸びた瞬間だけカードを出す
  ↓
Loop（PLG）        シェアを見た人が自分もやる → Dig に戻る
```

言語化は途中の工程であって、目的ではない。**目的はシェアされる資産になること**。
だから「採点して終わり」でも「プロファイルを表示して終わり」でもなく、
公開・シェア・再訪までを射程に入れる。

## 2. 競合地図

| 層 | 代表 | 何をするもの | 関係 |
|---|---|---|---|
| A. 構造化出力・修復 | Vercel AI SDK (`generateObject`/`streamObject`)、instructor-js、zod-gpt、reforge-ai、island-ai | zod スキーマでLLM出力を検証し、壊れたら直す・再試行する | **競合しない。土台として乗る**。ここは 2026 時点でコモディティで、`ai` を peer に置いた判断は正しい |
| B. Eval・採点基盤 | autoevals、promptfoo、Braintrust | **AI の出力**を採点し、実験を比較する | **評価対象が逆**。こちらは人の発言を採点して**本人に返す**。保存・表示・再挑戦が前提 |
| C. 面接/コーチング SaaS | Metaview 等の面接品質ツール、各種診断サービス | 完成品のプロダクト | 開発者が自分のプロダクトに組み込む手段がない |
| D. 素材 → 本人の言葉 → 公開資産 → シェア導線 | **見当たらない** | — | ここを取る |

A と B の間に、誰も置いていない層がある。A は「JSON が壊れないこと」までしか面倒を見ず、
B は「スコアが集計できること」までしか見ない。**その結果を本人に見せて、
本人が配りたくなるところまで**を扱うライブラリが無い。

## 3. なぜ勝てるか（差別化の柱）

1. **本人に返す前提の規律** — 未採点の軸を中立値で埋めない。失敗を型で返して保存させない。
   引用は必ず会話ログに戻して検証する（幻の根拠を本人に見せない）。
   Eval 系は集計できれば十分なので、ここまで作る動機がない
2. **儀式としての3候補** — 一発生成ではなく、選ばせて・却下させて・掘り直す。
   「自分で選んだ言葉」だけが本人の所有物になり、シェアされる
3. **シェアの節度** — 毎回勧めると無視される。確定した瞬間・伸びた瞬間だけ出す判定を持つ
4. **公開の安全弁** — 既定は非公開、ポリシーが知らないフィールドは公開されない、
   掘り方のプロンプトはクライアントに出ない
5. **プロンプトを同梱しない** — 質問文・掘り方・評価軸は各社の資産。持たないからこそ、
   競合するプロダクト同士でも同じ土台を使える

## 4. ターゲット

- **一次**: 自分のプロダクトに「自己分析・診断・1on1・面談」を入れたい TypeScript 開発者
  （学生向け / クリエイター・インフルエンサー向け / HR）
- **二次**: 自社プロダクト（corecord・prepwork）の共通土台
- **非ターゲット**: LLM の性能評価をしたい人（それは B の領域。autoevals を使うべき）

「インフルエンサーや学生を、その人の思想でブランディングする」プロダクトを作る人が、
プロンプトと意匠だけ書けば残りが揃っている状態を目指す。

## 5. 実証（ケーススタディ）

同じ土台の上に、語彙も成果物も違う2つが載っていることが最大の説得材料になる。

| | corecord | prepwork-ai-coach |
|---|---|---|
| 掘る | 1問1画面のテキスト面談 | Vapi の音声面接 |
| 言語化 | 核（一文）＋ 二つ名・物語・光と影 | 7軸スコア＋総評＋振り返りハイライト |
| ブランド | アーティスト名・レコード番号 | 公開プロフィール `/u/:handle` |
| シェア | 公開記録ページ `/r/:id` | 伸びた軸のシェアカード |
| ループ | 曲がシェアされ、聴いた人が掘る | カードから公開ページ → 自分も練習 |

## 6. ローンチ

1. README を5段ループの順に構成し、30行で動く Quickstart を先頭に置く
2. `docs/case-studies/` に上の2例（コードの引用付き）
3. 記事1本目：**「LLM に人を採点させるときにやってはいけないこと」**
   — 未採点軸を埋めない / 引用を検証する / 失敗を型で返す。差別化の核心がそのまま技術記事になる
4. 記事2本目：「言語化した結果をシェアさせる設計 — 毎回勧めない」
5. npm 公開 ＋ GitHub topics（`llm` `plg` `self-analysis` `interview` `zod` `ai-sdk`）
6. 日本語（Zenn）と英語（dev.to）の両方に出す。実利用2件が証明になる

## 7. 設計への反映

モジュールをループの段に沿って並べ替える（機能の寄せ集めではなく、順番のあるループとして読める形にする）。

```
core      text / sanitize / errors / generate / registry     … 土台（A層の上）
dig       transcript / flows                                 … 素材を集める
verbalize candidates(+refine) / modes / quotes               … 本人の言葉にする
brand     handle / visibility / profile columns              … 公開できる資産にする
share     pickImprovedAxis → shareMoment                     … 出す瞬間を選ぶ
react     useStagedReveal / useTypewriter / useCountUp       … 見せ方の振る舞い
```

`share` は現在 prepwork 由来の「伸びた軸」判定しか持っていないが、
corecord 側の「初めて確定した瞬間」も同じ**シェアの瞬間**なので、
`pickShareMoment({ improvement, isFirstResult, milestone })` に一般化する。
